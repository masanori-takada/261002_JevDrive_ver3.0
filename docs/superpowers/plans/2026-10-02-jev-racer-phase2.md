# JevDrive ver3.0 追加計画（フェーズ2）

作成日: 2026-10-02 / 作成: Sonnet 5.5 / 承認: ユーザー（「全て」）

## 目的

初回の完了報告で残した3つを片付ける。

1. 運転の効果を上げる（実 Jev で、衝突は距離 1 あたり 約 0.92 回。操作なしは約 1.19 回）
2. 検出の推論速度を縮める（平均 198.6ms。目標 50ms 以下）

## 進め方（初回と同じ）

- 役割: オーケストレーター（私。コードは書かない）／実装サブエージェント／最後にレビュー専用サブエージェント（実装者とは別）。エフォートは medium。
- 判断の分岐は Jev に問い合わせて続行する（`node scripts/ask-jev.mjs`、採用基準は確率 0.8 以上、判断は `docs/decisions/jev-log.md` に記録）。ただし push・削除・課金・認証情報・要件変更はユーザー本人の確認が必要。
- 各タスク完了時に、変更点とテスト結果を3行で要約する（停止はしない）。
- 初回の反省: 計画に完全なコードを書くと、計画側の誤りが混ざった。今回は「目的・制約・合格基準」を書き、実装サブエージェントが TDD でコードを書く。計画と実測が食い違ったら、黙って直さず報告させる。
- 共通の制約: 仕様書 `docs/superpowers/specs/2026-10-02-jev-racer-design.md` と、初回計画の Global Constraints。`.env.local` は読まない・値を表示しない。サブエージェントは git 操作をしない。`next dev` と `next build` は同時に動かさない（`.next` を共有）。

## P1: 基準ゲートの自動化（測定の土台）

**なぜ先か:** 速度改善（P2）と、将来の検出モデルの変更を、ブラウザを開かずに繰り返し測れるようにする。レビューの「基準ゲートを `npm test` 化」「適合率が未測定」にも対応する。

- `scripts/gate.ts`（`npm run gate`）: `makeScene(0..99)` を `@napi-rs/canvas` で描画（`renderGame`、自車なし、640×360 を 320×320 に引き伸ばす）→ `onnxruntime-node` で推論 → `decodeYolo` → `computeRecall`。再現率、**適合率（正解に一致しない検出の割合）**、平均推論時間を出力し、再現率 0.8 未満なら終了コード 1。
- 前処理は `src/vision/detector.ts` と同一にする（共通化できるなら純関数として切り出し、ブラウザ側とテストで共有する）。
- 合格基準: `npm run gate` が PASS（再現率 0.8 以上）。ブラウザ（/debug）の再現率（0.995）と大きくずれないこと（ずれたら前処理の差を調べて報告）。出力に Node CPU での平均推論時間を含める（ブラウザの値とは別物として扱う）。

## P2: 推論速度

**合格基準:** `/debug`（ブラウザ）の平均推論が下がること。目標は 50ms 以下だが、届かない場合は「どこまで下がったか」と手段ごとの実測を報告する。基準ゲート（再現率 0.8 以上）は維持する。

試す手段（効果の大きい順に実測し、効いたものを採用）:
1. WASM のマルチスレッド（`numThreads` を増やす）。`next.config.ts` に `Cross-Origin-Opener-Policy: same-origin` と `Cross-Origin-Embedder-Policy: require-corp` を付ける必要がある（付けても `/ort` や `/models` の配信が壊れないことを確認する）。
2. WebGPU 実行プロバイダ（`ort.webgpu.min.js` を使い、使えなければ WASM にフォールバック）。確認用ブラウザで使えるか不明なので、使えない場合は「未検証」と報告する。
3. 検出を Web Worker に移し、メインスレッドを塞がないようにする（遅延そのものは縮まないが、描画が滑らかになる）。1 と 2 で足りない場合のみ。
4. 入力サイズの縮小（256 など）。再学習が必要なので、1〜3 で目標に届かない場合のみ、Jev に問い合わせてから行う。

## P3: 運転の効果

**まず測る:** 操作なし・ルール式（現行）・改善案を、ブラウザ抜きの模擬実験（`scripts/sim.ts`）で比べる。ゲーム本体（`step`）を使い、検出は完全（遅延だけ模擬）として、判断の周期と遅延（約 600ms）を再現する。評価は「距離 1 あたりの衝突回数」を複数のシードで平均する。

**有力な改善案（ゲームの難易度ではなく、判断の構造）:** 現行は Jev の選択（左・直進・右）がそのまま次の判断まで保持され、遅延 0.5 秒の間にハンドルを切りっぱなしになる。代わりに Jev には **目標レーン（左・中央・右）と加減速** を選ばせ、フレームごとに動く低レベル制御が目標レーンへ操舵する（Jev＝高レベルの判断、制御＝実行）。

- 模擬実験で、現行方式と目標レーン方式を比べ、衝突が明確に減る（目安: 現行比 3 割以上）か確認する。
- ゲームの障害物密度（`SPAWN_GAP`）の調整は、デモとして成立する範囲に限り、Jev に問い合わせて決める。
- 採用した場合は、`Action` の契約（`src/lib/types.ts`）と `/api/systemone` の応答、Jev への質問（`src/server/jev.ts`）、`driver`・`RacerGame` を更新し、テストを書く。仕様書 §4 も更新する。
- **合格基準:** 模擬実験で改善が確認でき、実 Jev でブラウザ上の 65 秒運転を行って、距離あたりの衝突が操作なし（約 1.19）より明確に少なく、前回の実 Jev（約 0.92）より減ること。失敗 0・コンソールエラーなし。

## P4: レビューの未対応分

レビューレポート `docs/superpowers/reviews/2026-10-02-review.md` 末尾の「未対応」を片付ける。

- `ai` のバージョンを固定し（キャレットを外す）、`experimental_evaluate` が関数としてエクスポートされていることを確認するテストを足す（API 形状の変更を `npm test` で気付けるようにする）。
- Jev の 1000ms 打ち切りを `Promise.race` でも保証する。`driver` の `analyze()` にもタイムアウトを付け、ハングしても 3 分上限と失敗カウントが働くようにする。
- テストの漏れ: `instrumentation.ts`、`post.ts`、route のタイムアウトと `JEV_MODEL` 未設定。
- 要確認: キー未設定時に `instrumentation.ts` が `throw` したときの Next 16 の挙動（`AI_GATEWAY_API_KEY=` を空にして `next dev` を起動して確認し、結果を記録する）。実 Jev の衝突数・hold 率は P3 の合格確認で記録する。
